# 06 设备驱动

NuttX 的驱动在 `drivers/` 目录，通过"注册进 inode 树"与 VFS 集成。

## 1. 驱动模型总览

```
用户程序: open("/dev/ttyS0") → read() → write() → ioctl()
  │
  ▼
VFS: inode 查找 → file_operations 回调
  │
  ▼
驱动: xxx_open() xxx_read() xxx_write() xxx_ioctl()
  │
  ▼
硬件: 寄存器操作 / DMA / 中断
```

**核心机制：`register_driver()`** —— 把一个 `file_operations` 函数表 + 私有数据挂到 `/dev/xxx` 节点：

```c
int register_driver(FAR const char *path,
                    FAR const struct file_operations *fops,
                    mode_t mode, FAR void *priv);
// include/nuttx/fs/fs.h 声明，fs/driver/fs_registerdriver.c 实现
```

- `path`：如 "/dev/ttyS0"、"dev/led0"（注意：不带前导斜杠的写法也会被规范化）
- `fops`：驱动的 open/close/read/write/ioctl/... 函数表
- `priv`：驱动私有数据（如 `struct uart_dev_s *`），存入 inode 的 `i_private`

## 2. file_operations 与驱动私有结构

驱动惯用模式：**一个私有结构体保存硬件状态 + 一个 fops 表**。

以串口为例（drivers/serial/serial.c，NuttX 串口框架）：

```c
struct uart_dev_s
{
  /* 硬件抽象层回调（由具体芯片实现） */
  FAR const struct uart_ops_s *ops;   // setup/shutdown/attach/detach/...
  /* 收发缓冲 */
  struct uart_buffer_s xmit;   // 发送环形缓冲
  struct uart_buffer_s recv;   // 接收环形缓冲
  /* 中断相关 */
  FAR void *priv;              // 芯片私有数据（寄存器基址等）
  ...
};

static const struct file_operations g_serial_fops =
{
  serial_open,   // open
  serial_close,  // close
  serial_read,   // read
  serial_write,  // write
  ...
};
```

- 具体芯片驱动（如 `arch/arm/src/stm32/stm32_serial.c`）实现 `uart_ops_s`（`uart_attach`、`uart_txready`、`uart_send`、`uart_rxint`...），把中断与缓冲框架绑定
- 框架层处理环形缓冲、流控、tty 语义；芯片层只碰寄存器
- 这就是 NuttX 串口"两级结构"：`serial.c`（通用）+ `stm32_serial.c`（芯片相关）

## 3. 驱动注册的三个层次

```
drivers_early_initialize()      // 启动早期：时钟、基础串口等（drivers/early_initialize.c）
  ├─ 由 nx_start() 调用（见 02_启动流程.md）
  └─ 注册 /dev/console 等

devnull_register() / zero_register()  // 杂项设备（drivers/misc/devnull.c 等）

board_app_initialize()          // 板级应用初始化（boards/.../src/）
  ├─ 由 nx_bringup() 调用
  └─ 注册该板子特有的外设驱动（SPI、I2C、GPIO、显示等）
```

查找注册点：`grep -rn "register_driver" boards/ drivers/ | grep -v ".o:"`

## 5. 块设备与字符设备

- **字符设备**：`file_operations` 直接挂在 inode 上（上面讲的都是）
- **块设备**：`struct block_operations`（open/close/read/write/geometry/ioctl），用 `register_blockdriver()` 注册
- 块设备通过 `mkfs` 格式化后挂载为文件系统（05_文件系统.md）
- `fs/driver/fs_blockproxy.c`：块设备代理，让块设备也能按字符方式读写（如 /dev/mtdblockX）

## 6. ioctl 命令约定

驱动 ioctl 的命令号定义在 `include/nuttx/ioctl.h`：

```c
#define _TIOC(n)   _IOC(_TIOCBASE, n)   // 终端类
#define _DIOC(n)   _IOC(_DIOCBASE, n)   // 磁盘类
#define _BIOC(n)   _IOC(_BIOCBASE, n)   // 块设备类
...
```

用户态 `ioctl(fd, cmd, arg)` → VFS `fs_ioctl.c` → `f_ops->ioctl()`。
驱动里用 switch(cmd) 分发，注意 cmd 可能被 `_IOC` 编码，用 `_IOC(cmd)` 解出类型。

## 7. 中断与驱动

- 驱动在 open 时 `irq_attach(irq, handler, dev)` 挂中断
- 中断处理（ISR）里只做最少工作：清标志、把数据塞进环形缓冲、唤醒等待线程
- 底半部：NuttX 用"工作队列"（workqueue，sched/wqueue/）实现，`work_queue()` 把延后处理挂到内核/HP 工作线程
- 例：串口接收中断 → `uart_rxint` → 数据入 recv 环形缓冲 → `sem_post` 唤醒 read 阻塞的任务

## 8. 中断处理的完整链路（以串口接收为例）

```
硬件中断
  └─> 架构中断入口（arch/arm/src/common/arm_vector.S 等）
        └─> 中断分发: arm_decodeirq() / up_irq_dispatch()
              └─> 驱动 ISR: stm32_serial.c 的串口 ISR
                    └─> 通用串口框架: uart_rxavailable() → uart_recvchars()
                          └─> 数据入环形缓冲 + 唤醒等待者（sem_post）
                                └─> 被唤醒的 read() 任务从缓冲取数据返回
```

阅读建议：跟着一个最简单的中断驱动（如 GPIO 按键中断或串口）走完这条链。

## 9. 建议阅读顺序

1. `drivers/serial/serial.c` —— 串口框架（最典型的两级驱动结构）
2. `drivers/misc/devnull.c` —— 最简单的驱动（几行代码）
3. `fs/driver/fs_registerdriver.c` —— 注册机制本身
4. 挑一个芯片串口驱动：`arch/<arch>/src/<chip>/<chip>_serial.c`（对照框架读）
5. `drivers/gpio/gpio.c` —— ioctl 型驱动的典型
6. 需要时看 `drivers/mmcsd/`（块设备+中断+DMA 的综合体）

## 10. 动手实验

- 在任意板子上 `ls /dev`，观察注册出来的设备节点
- `grep -rn "register_driver" drivers/ | head` 看都有谁注册了设备
- 给自己的板子加一个 LED 驱动：模仿 `drivers/misc/` 下最简单的驱动，注册 `/dev/led0`
