# 08 系统调用机制

NuttX 的"系统调用"层在 `syscall/` 目录，是用户态 API 与内核实现之间的桥梁。

## 1. 三种构建模式

NuttX 有三种构建模式（Kconfig 中的 `CONFIG_BUILD_FLAT/PROTECTED/KERNEL`）：

| 模式 | 说明 | syscall 的作用 |
|------|------|----------------|
| FLAT | 全部代码链接成一个镜像，无特权级分离 | 无 trap，函数直接调用（本仓库当前配置即此模式） |
| PROTECTED | 用户态/内核态分离，内核用 MPU 保护 | syscall 通过 SVC/trap 陷入内核 |
| KERNEL | 完整内核模式，用户态独立地址空间 | 同上，更彻底 |

**即使 FLAT 模式下，syscall 层的代码生成机制仍然存在**，理解它对读 libc → 内核的路径很有帮助。

## 2. syscall.csv —— 系统调用总表

`syscall/syscall.csv` 是**唯一的系统调用定义源**，每行描述一个调用：

```
"函数名","头文件","使能条件","返回类型","参数1","参数2",...
```

示例（本仓库实际内容）：

```
"_assert","assert.h","","void","FAR const char *","int","FAR const char *","FAR void *"
"accept4","sys/socket.h","defined(CONFIG_NET)","int","int","FAR struct sockaddr *","FAR socklen_t *","int"
```

- 第三列的 `defined(CONFIG_XXX)` 表示该调用只在相应配置下编译
- 带下划线前缀的（`_assert`、`_exit`）是内部函数，不暴露为公共 API

## 3. 代码生成工具 mksyscall

`tools/mksyscall.c`（宿主机工具，配合 tools/csvparser.c）解析 syscall.csv，
自动生成四类代码：

```
syscall/
├── stubs/   用户态桩（每个 syscall 一个 .c）
├── proxies/ 内核态代理（每个 syscall 一个 .c）
├── wraps/   包装函数（FLAT 模式直接转发）
├── syscall_names.c        编号 → 名字表（调试用）
├── syscall_stublookup.c   syscall 编号 → 桩函数指针表
└── syscall_wraps.h        包装函数声明
```

生成流程：`make` 时先编译 mksyscall（tools/Makefile.host），再运行它解析
syscall.csv（syscall/Makefile 中的 `.context` 目标）。

## 4. syscall 编号与查找

- 每个 syscall 有一个编译期编号（`SYS_xxx` 宏，生成在 `include/sys/syscall.h`）
- `syscall_stublookup.c` 提供 `g_stublookup[]`：编号 → 处理函数
- 用户态调用流程（PROTECTED/KERNEL 模式）：

```
用户态: open()  [libs/libc/...]
  └─> stub: syscall(SYS_open, ...)   // 触发 SVC/trap 指令
        └─> 内核 trap handler (arch/<arch>/src/common/arm_syscall.c 等)
              └─> 按编号查 g_stublookup[] → proxy: nx_open(...)
                    └─> 返回用户态
```

- FLAT 模式：wraps 直接调用内核函数（`#define open nx_open` 之类），无陷入开销

## 5. 为什么 libc 的函数名和内核函数名不一样

NuttX 的命名约定（贯穿全仓库）：

| 前缀 | 含义 | 例子 |
|------|------|------|
| （无前缀） | 用户态 POSIX API | open(), read(), sem_wait() |
| nx_ / nxsem_ / nxsig_ / nxtask_ / nxsched_ | 内核内部实现（不设置 errno，或在 libc 包装） | nx_open(), nxsem_wait() |
| psock_ / file_ | 内部更细粒度实现 | file_read(), psock_send() |

例如：
- `libs/libc/stdio/lib_printf.c` → `lib_vsprintf` → 最终调 `write()` → 用户态 stub
- 内核里实际干活的是 `fs/vfs/fs_write.c` 的 `file_write()`，被 `nx_write()` 包装

## 6. 用户态与内核态的边界（PROTECTED/KERNEL）

- 用户态：libs/libc + 应用代码，运行在非特权模式
- 内核态：sched/、fs/、drivers/、net/、mm/ 等，运行在特权模式
- 边界 = syscall 层：用户态只能通过 syscall 触及内核
- 数据结构传递：参数按值传递，指针指向用户空间，内核里用 `copy_from_user` 类机制（mm/ 相关）校验
- 这个模式下每个进程有独立的地址空间（arch 的 MPU/MMU 支持）

## 7. 建议阅读顺序

1. `syscall/syscall.csv` —— 看 100 行，感受 API 面
2. `tools/mksyscall.c` —— 只读 main 函数，理解生成逻辑（不细读）
3. `syscall/syscall_names.c` —— 看生成的编号表
4. 找一个简单 syscall 的完整路径：如 `_exit`：
   - 用户态：`libs/libc/unistd/lib_exit.c` → `syscall(SYS__exit,...)`
   - 内核：`sched/task/task_exit.c` → `nxtask_exit()`
5. 若用 PROTECTED/KERNEL 模式，再读 `arch/<arch>/src/common/<arch>_syscall.c` 的 trap 处理
