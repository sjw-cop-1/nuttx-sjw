# NuttX 源码逻辑阅读指南（M144Z-M3 / STM32F103ZET6）

> 本文是《NuttX 源码学习文档》第 14 篇。目标不是裁剪代码，而是给你一条
> **最短理解路径**：看懂 NuttX 在正点原子 M144Z-M3（STM32F103ZET6，Cortex-M3）
> 这块板子上从上电到跑起 NSH 的全过程。
>
> 所有路径均为本仓库真实路径，已核对（NuttX 13.0.1-RC0）。

## 0. 先说一件会救你很多时间的事：这份代码树的布局

你手上这份是 **STM32 架构统一化重构后**的 NuttX（13.0.1-RC0），
和网上大多数教程/主线 12.x 的目录**不一样**。对照表：

| 概念 | 主线 12.x 的位置 | **你这份仓库的位置** |
|---|---|---|
| Cortex-M3 内核支持 | `arch/arm/src/armv7-m/` | 一样 `arch/arm/src/armv7-m/` |
| STM32 家族公共代码 | `arch/arm/src/stm32/stm32_*.c`（扁平） | **`arch/arm/src/common/stm32/stm32_*_m3m4_v1.c`**（按 IP 核版本命名） |
| STM32F1 专属代码 | `arch/arm/src/stm32/`（混在一起） | **`arch/arm/src/stm32f1/`**（只剩 RCC + 寄存器头） |
| F1 板子 BSP | `boards/arm/stm32/<board>/` | **`boards/arm/stm32f1/<board>/`** |

所以当你看到别的教程说“去看 `arch/arm/src/stm32/stm32_start.c`”，
在你这里对应的是 `arch/arm/src/common/stm32/stm32_start_m3m4_v1.c`。
文件名里的 `m3m4_v1` = “Cortex-M3/M4 系列、第 1 版外设 IP 核”，
`configure` 时由 Kconfig 的 `STM32_HAVE_IP_*` 选项决定编哪个变体。

另外，`configure.sh` 会创建两个关键软链，让“通用名字”指向“你的芯片”：

```
arch/arm/src/chip      -> arch/arm/src/stm32f1
arch/arm/include/chip  -> arch/arm/include/stm32f1
```

代码里 `#include "chip.h"` / `arch/chip/xxx.h` 就是通过它们落到 stm32f1 的。

## 1. NuttX 软件分层架构

从硅片到你敲的命令，一共 7 层。左边是层，右边是**本仓库对应目录**：

```
┌─────────────────────────────────────────────────────────────────────┐
│ 7. 应用层        apps/  (独立仓库, 在 ../apps)                        │
│    NSH shell / 示例 / 网络工具 …          apps/system/nsh, apps/nshlib│
├─────────────────────────────────────────────────────────────────────┤
│ 6. C 库 / 系统调用    libs/libc/   syscall/   （POSIX/ANSI API 实现） │
├─────────────────────────────────────────────────────────────────────┤
│ 5. 系统服务层                                                        │
│    文件系统 VFS      fs/            （/dev, procfs, 挂载点）          │
│    内存管理          mm/            （堆分配器 mm_heap）              │
│    网络协议栈        net/            （本板未启用）                   │
│    设备驱动上半部    drivers/        （serial/, leds/, …）            │
├─────────────────────────────────────────────────────────────────────┤
│ 4. 内核核心层        sched/                                          │
│    调度器 / 任务 / 信号量 / 时钟 / 工作队列 / 看门狗定时器           │
│    OS 启动           sched/init/  (nx_start.c, nx_bringup.c)         │
├─────────────────────────────────────────────────────────────────────┤
│ 3. 板级支持层 (BSP)  boards/arm/stm32f1/m144z-m3/                    │
│    时钟参数 / 引脚复用 / LED / 按键 / 链接脚本 / 板级初始化钩子      │
│    公共部分          boards/arm/stm32f1/common/                      │
├─────────────────────────────────────────────────────────────────────┤
│ 2. 芯片驱动层 (chip)                                                 │
│    F1 专属：RCC 时钟、寄存器定义   arch/arm/src/stm32f1/             │
│                                    arch/arm/src/stm32f1/hardware/    │
│    STM32 公共：启动、串口、GPIO、  arch/arm/src/common/stm32/        │
│    Flash、定时器、DMA … (按 IP 核版本选变体)                        │
├─────────────────────────────────────────────────────────────────────┤
│ 1. 架构抽象层 (arch)  Cortex-M3 / ARMv7-M                            │
│    向量表 / 异常入口 / NVIC / SysTick / SVC 上下文切换               │
│                      arch/arm/src/armv7-m/                           │
│    ARM 通用           arch/arm/src/common/  (arm_initialize.c 等)    │
│    架构对外头文件     arch/arm/include/armv7-m/, arch/arm/include/   │
├─────────────────────────────────────────────────────────────────────┤
│ 0. 硬件              STM32F103ZET6：Cortex-M3 @72MHz                 │
│                      512KB Flash @0x08000000 / 64KB SRAM @0x20000000 │
└─────────────────────────────────────────────────────────────────────┘
```

**关键心智模型**：NuttX 驱动普遍是“上半部/下半部”（upper-half / lower-half）：

- 上半部：架构无关，注册字符设备节点、处理 `read()/write()/ioctl()`
  → 在 `drivers/`（如 `drivers/serial/serial.c`）
- 下半部：芯片相关，真正碰寄存器、处理中断
  → 在 `arch/arm/src/common/stm32/`（如 `stm32_serial_m3m4_v1v2v3v4.c`）

两者通过一个 `struct ops` 函数指针表对接。理解了这一点，看任何驱动都不迷路。

## 2. 你这块板子的核心代码路径（逻辑最小集）

### 2.1 架构层 `arch/arm/src/armv7-m/`（Cortex-M3 内核）

| 文件 | 作用 |
|---|---|
| `arm_vectors.c` | **中断向量表** `_vectors[]`，放在 `.vectors` 段（Flash 最前）。`[0]`=初始 MSP，`[1]`=复位向量→本文件里的 `start()`（内联汇编 `b __start`）；`[2..]`=`exception_common`/`exception_direct` |
| `arm_exception.S` | 所有异常/中断的统一汇编入口 `exception_common`：保存现场 → 调 `arm_doirq()` → 恢复现场。**上下文切换的实际发生地** |
| `arm_doirq.c` | C 层中断分发，调用 `irq_dispatch()` 找到已注册的 handler |
| `arm_svcall.c` | `SVC` 系统调用/上下文切换请求的处理 |
| `arm_systick.c` | SysTick 定时器 → 产生 OS 系统节拍（`nxsched_process_timer`） |
| `arm_initialstate.c` | 新任务的初始寄存器现场（假装它“曾被中断过”，第一次调度即可弹入） |
| `arm_schedulesigaction.c` | 给运行中的任务“插入”信号处理 |
| `nvic.h`（在 `arch/arm/include/armv7-m/`）| NVIC 寄存器定义 |

### 2.2 芯片层

**F1 专属 `arch/arm/src/stm32f1/`：**

| 文件 | 作用 |
|---|---|
| `stm32_rcc.c` | `stm32_clockconfig()` —— 时钟总入口：复位 RCC → 调 `stm32_stdclockconfig()` |
| `stm32f10xxx_rcc.c` | `stm32_stdclockconfig()` —— **真正写 RCC 寄存器**：开 HSE、配 PLL（用 `board.h` 里的宏 `STM32_PLL_FREQUENCY` 等）、切 SYSCLK、配 AHB/APB 分频、Flash 等待周期 |
| `chip.h` / `stm32.h` | 汇总头，`#include` 具体外设寄存器头 |
| `hardware/stm32f103xx_*.h` | F103 各外设寄存器地址/位定义 |

**STM32 公共 `arch/arm/src/common/stm32/`（本板实际会编到的）：**

| 文件 | 作用 |
|---|---|
| `stm32_start_m3m4_v1.c` | **C 语言启动入口 `__start()`**（见第 3 节） |
| `stm32_gpio_m3m4_v1v2.c` | `stm32_configgpio()` / `stm32_gpiowrite()` / `stm32_gpioread()` —— GPIO 底层 |
| `stm32_lowputc_usart_m3m4_v1v2v3v4.c` | `arm_lowputc()` —— 最早期的“单字符打印”，启动阶段调试用 |
| `stm32_serial_m3m4_v1v2v3v4.c` | **USART 驱动下半部**：中断收发、`/dev/ttyS0`、`/dev/console` |
| `stm32_irq_m3m4_v1.c` | `up_irqinitialize()` —— 初始化 NVIC、设置优先级、`arm_ack_irq` 等 |
| `stm32_timerisr_armv7m.c` | `up_timer_initialize()` —— 配 SysTick 频率（依据 `CONFIG_USEC_PER_TICK`） |
| `stm32_allocateheap_m3m4_v1.c` | `up_allocate_heap()` —— 告诉内核 SRAM 里堆的起止地址 |

| `stm32_flash_m3m4_f1f3.c` | Flash 擦写（本最小系统未用到 progmem 时不编） |

### 2.3 板级层 `boards/arm/stm32f1/m144z-m3/`

| 文件 | 作用 |
|---|---|
| `include/board.h` | **时钟树参数**（HSE 8MHz ×9 = 72MHz）、LED/按键编号、**引脚复用**（USART1=PA9/PA10 等）。芯片层代码 `#include <arch/board/board.h>` 读它 |
| `src/m144z-m3.h` | 板内部私有定义：`GPIO_LED0=PB5`、`GPIO_LED1=PE5`、`KEY0=PE4`、procfs 挂载点等 |
| `src/stm32_boot.c` | `stm32_boardinitialize()` —— **最早的板级钩子**，由 `__start()` 调用，一般在这里点亮/初始化 LED、必要时初始化片外 SRAM/FSMC |
| `src/stm32_bringup.c` | `stm32_bringup()` —— **较晚的板级初始化**，由 `board_late_initialize()` 调用：挂 procfs、注册 `/dev/userleds` 等 |
| `src/stm32_autoleds.c` | `CONFIG_ARCH_LEDS=y` 时编：内核状态机驱动 LED（心跳、panic 闪烁） |
| `src/stm32_userleds.c` | 不用 autoleds 时编：把 LED 作为 `/dev/userleds` 给应用控制 |
| `src/stm32_buttons.c` | `CONFIG_ARCH_BUTTONS=y` 时编：KEY0 读取/中断 |
| `scripts/ld.script` | **链接脚本**：`flash 512K @0x08000000` / `sram 64K @0x20000000`，`.vectors` 放最前，`.text/.data/.bss` 布局 |
| `scripts/Make.defs` | 本板的编译/链接开关：引入 `armv7-m/Toolchain.defs`，指定 `LDSCRIPT`，拼 `CFLAGS` |
| `configs/nsh/defconfig` | **唯一配置文件**（见第 5 节） |
| `Kconfig` | 本板可加的自定义配置项（目前为空） |

公共部分 `boards/arm/stm32f1/common/`：F1 系列多块板共用的 `stm32_appinit()` 等
（`CONFIG_ARCH_BOARD_COMMON=y` 时参与编译）。

### 2.4 内核层 `sched/`（必须理解的调度器核心）

| 文件 | 作用 |
|---|---|
| `sched/init/nx_start.c` | **`nx_start()`** —— OS 初始化总流程（堆、任务表、`up_initialize()`、`nx_bringup()`） |
| `sched/init/nx_bringup.c` | 启动工作队列 + **spawn 第一个用户任务**（`nsh_main`） |
| `sched/sched/sched_addreadytorun.c` | 把任务加入“就绪链表”，**并判断是否需要抢占**当前任务 |
| `sched/sched/sched_removereadytorun.c` | 任务阻塞/退出时移出就绪链表，挑下一个来跑 |
| `sched/sched/sched_mergepending.c` | 临界区结束后把“挂起的就绪任务”合并进就绪链表 |
| `sched/sched/sched_switchcontext.c` | 触发一次上下文切换（最终落到 `arm_svcall.c` / PendSV） |
| `sched/sched/sched_roundrobin.c` | 同优先级时间片轮转（`CONFIG_RR_INTERVAL`） |
| `sched/task/task_start.c` | 每个任务的“外壳函数”：调用 `entry(argc,argv)`，返回后 `exit()` |
| `sched/task/task_setup.c` | 任务创建时挂进各种链表、分配 PID/TLS |
| `sched/semaphore/sem_wait.c` / `sem_post.c` | 阻塞/唤醒的最基本原语——**大多数调度切换是它们触发的** |
| `sched/clock/clock_initialize.c` | 系统时间基准；配合 `arm_systick.c` 的节拍中断 |
| `sched/wdog/wd_start.c` | 看门狗定时器（内核内部超时机制，非硬件 IWDG） |

> 就绪链表 `g_readytorun` 是**按优先级排序的单链表**，表头就是“当前正在跑的任务”。
> 理解 `sched_addreadytorun` / `sched_removereadytorun` 这两个函数 = 理解 NuttX 调度器 80%。

## 3. 系统启动流程（主干调用链）

从上电到 NSH 提示符，跟着控制流走一遍。**每一步都标了文件:函数**。

```
【硬件】上电/复位
   │  Cortex-M3 硬件动作(没有指令、代码里搜不到)：
   │    MSP ← [0x08000000] = _vectors[0] = IDLE_STACK
   │    PC  ← [0x08000004] = _vectors[1] = &start
   ▼
start()                            arch/arm/src/armv7-m/arm_vectors.c:61
   │  static void start(void)，就是 _vectors[1] 指向的“复位向量函数”
   │  asm volatile("mov lr, #0 \n\t"   ← LR 清零，backtrace 到此为止
   │               "b  __start \n\t"); ← 内联汇编分支(b，非 bl)到 __start
   │  ↑ 这条“跳转”在 asm 字符串里，Understand/ctags 等 C 分析器看不到，
   │    所以你在代码里找不到“__start 被谁调用”——它是被硬件+一条 b 指令进入的。
   ▼
__start()                          arch/arm/src/common/stm32/stm32_start_m3m4_v1.c:114
   │  1. 设定 MSP、清 .bss、从 Flash 拷 .data 到 SRAM
   │  2. showprogress('A'..)  —— 经 arm_lowputc() 从 USART1 吐字符，肉眼可见启动进度
   │  3. stm32_clockconfig()        arch/arm/src/stm32f1/stm32_rcc.c:153
   │        └─ stm32_stdclockconfig()  arch/arm/src/stm32f1/stm32f10xxx_rcc.c:527
   │             开 HSE(8MHz) → 配 PLL×9 → SYSCLK=72MHz → AHB/APB 分频 → Flash 2 等待
   │  4. arm_earlyserialinit() / stm32_lowsetup()  —— 早期串口，供 syslog
   │  5. stm32_gpioinit()            —— GPIO 时钟/复用基础
   │  6. arm_boardinitialize()  ──►  stm32_boardinitialize()
   │                                 boards/arm/stm32f1/m144z-m3/src/stm32_boot.c
   │                                 （板级最早钩子：LED 初始化等）
   ▼
nx_start()                         sched/init/nx_start.c:502
   │  1. 初始化 idle 任务 TCB（PID 0）、任务链表
   │  2. mm_initialize() / kmm_initialize()  —— 建立 SRAM 堆
   │  3. 各子系统 initialize：信号量、时钟、信号、工作队列、VFS(fs_initialize)、binfmt…
   │  4. up_initialize()            arch/arm/src/common/arm_initialize.c:62
   │        └─ up_irqinitialize()(NVIC)、up_timer_initialize()(SysTick)、
   │           arm_serialinit()(注册 /dev/console、/dev/ttyS0)、devnull/devzero…
   │  5. board_early_initialize()   （本板未定义，空）
   │  6. nx_bringup()
   ▼
nx_bringup()                       sched/init/nx_bringup.c
   │  1. board_late_initialize()  ──►  stm32_bringup()
   │                                  boards/arm/stm32f1/m144z-m3/src/stm32_bringup.c
   │                                  （挂 procfs、注册 /dev/userleds…）
   │  2. nx_start_application()：
   │        task_spawn("nsh_main", nsh_main, ...,     nx_bringup.c:354
   │                   优先级=100, 栈=CONFIG_INIT_STACKSIZE=2048)
   │        —— 这个新任务一旦就绪且优先级 > idle，调度器立刻切过去
   ▼
（nx_start 尾部）idle 任务进入 up_idle() 死循环   arch/arm/src/common/stm32/stm32_idle_m3m4_v1.c
                 —— 从此 CPU 要么跑 nsh，要么跑中断，要么在 idle

═══════════ 调度器切到新任务 ═══════════

task_start()                       sched/task/task_start.c
   │  调用任务入口
   ▼
nsh_main(argc, argv)               apps/system/nsh/nsh_main.c:44
   │  1. nsh_initialize()           apps/nshlib/nsh_init.c
   │  2. nsh_consolemain()          apps/nshlib/nsh_consolemain.c:64
   ▼
nsh_consolemain()
   │  打开 /dev/console（= USART1）
   │  nsh_session() 主循环         apps/nshlib/nsh_session.c
   │     └─ 打印 "nsh> " → readline() 读串口
   │        └─ nsh_parse()          apps/nshlib/nsh_parse.c
   │           └─ nsh_command()     apps/nshlib/nsh_command.c   （内置命令）
   │              或 exec_builtin() apps/builtin/exec_builtin.c （builtin 程序）
   ▼
【你看到】 nsh>
```

关键理解点：

- **没有独立的 `startup_stm32f103xe.s`**。ARMv7-M 的向量表是 C 数组 `_vectors[]`
  （`arm_vectors.c:91`，`locate_data(".vectors")` → 被 `ld.script` 的 `*(.vectors)`
  钉在 `0x08000000`）。`_vectors[1]` 指向同文件里的 `static void start(void)`
  （`arm_vectors.c:61`），它只做两件事：`mov lr,#0` + `b __start`。
- **为什么工具找不到 `__start` 的调用处**：① CPU 取向量表是硬件行为，没有指令；
  ② `start → __start` 是内联汇编里的 `b` 分支，C 语义分析器不解析 `asm("...")`
  字符串。`grep __start` 在 arch 里只会命中 `arm_vectors.c` 的 `extern` 声明和那句
  `"b __start"`，以及 `stm32_start_m3m4_v1.c` 里的定义本身——因为它压根不是 C 调用。
- `__start` 里**先配时钟再干别的**——否则后面所有外设时序都是错的。
- `nsh_main` 不是被“调用”的，是被 `task_spawn()` **作为一个独立任务创建**的；
  `main()` 概念在 NuttX 里被 `CONFIG_INIT_ENTRYPOINT` 取代。

## 4. “最小理解集” —— 只看这 10 个文件

按**阅读顺序**排列。看完这 10 个，你就能在脑子里跑通这块板子的 NuttX。

| # | 文件 | 为什么先看它 / 看什么 |
|---|---|---|
| 1 | `boards/arm/stm32f1/m144z-m3/scripts/ld.script` | 先建立“物理地图”：Flash/RAM 地址与大小、`.vectors` 在最前、`_sbss/_ebss/_sdata` 这些符号——启动代码要用它们 |
| 2 | `boards/arm/stm32f1/m144z-m3/include/board.h` | 时钟树全貌（8MHz→72MHz 怎么算的）、USART1/LED/KEY 用哪些引脚。**一页纸看懂硬件** |
| 3 | `arch/arm/src/armv7-m/arm_vectors.c` | Cortex-M3 向量表长啥样、`_vectors[1]=start()` 如何用 `b __start` 进 C 世界、中断怎么进 `exception_common` |
| 4 | `arch/arm/src/common/stm32/stm32_start_m3m4_v1.c` | `__start()` 全文——C 世界的第一行代码，看它怎么一步步把机器带起来最后交给 `nx_start()` |
| 5 | `arch/arm/src/stm32f1/stm32f10xxx_rcc.c` （`stm32_stdclockconfig`） | 时钟到底怎么配的：HSE→PLL→SYSCLK→分频→Flash 等待。配合 #2 的宏一起看 |
| 6 | `boards/arm/stm32f1/m144z-m3/src/stm32_boot.c` | 板级最早钩子。看 BSP 是如何“插进”启动流程的（`arm_boardinitialize` 回调） |
| 7 | `sched/init/nx_start.c` | **内核初始化主线**。堆、任务表、`up_initialize()`、子系统 init 的顺序——顺序很有讲究 |
| 8 | `sched/init/nx_bringup.c` | 第一个用户任务是怎么、以什么参数被 spawn 出来的；`board_late_initialize` 在这里 |
| 9 | `boards/arm/stm32f1/m144z-m3/src/stm32_bringup.c` | 板级“晚期”初始化。以后你要加传感器/文件系统驱动，就往这里加 |
| 10 | `apps/system/nsh/nsh_main.c` （+ 顺手扫一眼 `apps/nshlib/nsh_consolemain.c`） | 应用侧入口。看 NSH 如何拿到 `/dev/console` 并进入命令循环 |

**加餐（想深入某方面时再看）：**

- 串口驱动上下半部：`drivers/serial/serial.c` + `arch/arm/src/common/stm32/stm32_serial_m3m4_v1v2v3v4.c`
- 调度器：`sched/sched/sched_addreadytorun.c` + `sched/semaphore/sem_wait.c` + `arch/arm/src/armv7-m/arm_exception.S`
- GPIO/LED 实操：`arch/arm/src/common/stm32/stm32_gpio_m3m4_v1v2.c` + `boards/.../src/stm32_autoleds.c`（另见 `Study/13_点亮LED实操教程.md`）

## 5. 构建系统：Makefile + Kconfig 如何把这一切串成一个 `nuttx`

### 5.1 三个角色

| 角色 | 是什么 | 作用 |
|---|---|---|
| **Kconfig** | 一棵以 `nuttx/Kconfig` 为根、`source` 出去的配置**规则树** | 定义“有哪些开关、依赖谁、默认值多少”。`menuconfig` 就是在这棵树的约束下编辑 `.config` |
| **`.config`** | 根目录一个扁平文本，一堆 `CONFIG_XXX=y` / `="str"` / `=123` | 本次构建的**最终选择**。被所有 Makefile / Make.defs `include`；又经 `tools/mkconfig` 生成 `include/nuttx/config.h`（C 代码看到的 `#define CONFIG_XXX`） |
| **Make.defs** | 一串 `include` 链，最终由板子的 `scripts/Make.defs` 收口 | 提供**编译/链接参数**：交叉编译器前缀、`-mcpu=cortex-m3 -mthumb`、优化级别、`LDSCRIPT`、`CFLAGS/LDFLAGS` |

### 5.2 `configure.sh m144z-m3:nsh` 做了什么

```
1. 找到 boards/arm/stm32f1/m144z-m3/configs/nsh/defconfig
2. 展开成完整 .config（olddefconfig：补齐所有未写的默认值）
3. 建软链，让“通用路径”指向本芯片/本板：
     include/arch            -> arch/arm/include
     arch/arm/include/chip   -> arch/arm/include/stm32f1
     arch/arm/src/chip       -> arch/arm/src/stm32f1
     include/arch/board      -> boards/arm/stm32f1/m144z-m3/include
     ./Make.defs             -> boards/arm/stm32f1/m144z-m3/scripts/Make.defs
4. 写 .version、生成初始依赖
```

### 5.3 `make` 时，配置如何“映射”到编译哪些文件

自顶向下：

```
顶层 Makefile
  └─ include .config              # 拿到所有 CONFIG_*
  └─ include Make.defs            # (软链→板子 scripts/Make.defs)
        └─ include arch/arm/src/armv7-m/Toolchain.defs   # CROSSDEV, -mcpu=cortex-m3 ...
  └─ 遍历各子目录，每个目录一个 Makefile / Make.defs：
        sched/Makefile      → 按 CONFIG_* 决定 CSRCS，编成 sched/libsched.a
        mm/Makefile         → mm/libmm.a
        fs/Makefile         → fs/libfs.a
        drivers/Makefile    → drivers/libdrivers.a   (serial 因 CONFIG_STANDARD_SERIAL=y 进来)
        libs/libc/Makefile  → libs/libc/libc.a
        arch/arm/src/Makefile
           └─ include chip/Make.defs         # = stm32f1/Make.defs
                └─ CHIP_CSRCS = stm32_rcc.c
                └─ include common/stm32/Make.defs
                     # 一大堆 ifeq($(CONFIG_STM32_HAVE_IP_xxx),y) 决定编哪个 _m3m4_vN.c
                     # 本板结果：stm32_start_m3m4_v1.c, stm32_gpio_m3m4_v1v2.c,
                     #           stm32_serial_m3m4_v1v2v3v4.c, stm32_irq_m3m4_v1.c,
                     #           stm32_timerisr_armv7m.c, stm32_allocateheap_m3m4_v1.c ...
           └─ + armv7-m/*.c + common/arm_*.c   → arch/arm/src/libarch.a
        boards/arm/stm32f1/m144z-m3/src/Makefile → libboard.a
  └─ apps/  (由 CONFIG_APPS_DIR 指到 ../apps)
        apps/Makefile + Application.mk
        CONFIG_SYSTEM_NSH=y      → 编 apps/system/nsh
        CONFIG_NSH_LIBRARY=y     → 编 apps/nshlib
        CONFIG_BUILTIN=y         → 生成 apps/builtin/builtin_list.c（含 "nsh" 条目）
        全部打包 → libapps.a

链接阶段：
  ld -T boards/arm/stm32f1/m144z-m3/scripts/ld.script \
     staging/*.a (libsched libmm libfs libdrivers libc libarch libboard libapps ...) \
     -o nuttx
  arm-none-eabi-objcopy -O binary  nuttx nuttx.bin
  arm-none-eabi-objcopy -O ihex    nuttx nuttx.hex
```

一句话：**`Kconfig` 定义可能性 → `.config` 拍板 → Makefile/Make.defs 里成百上千的
`ifeq ($(CONFIG_...),y)` 把对应 `.c` 加进编译列表 → 各目录编成 `.a` → 用板子的
`ld.script` 链成 `nuttx` ELF。** 没有任何文件是“被删掉”的，只是没被 `ifeq` 选中而已。

### 5.4 想验证“某个 CONFIG 影响了哪些文件”

```bash
# 看某选项当前值
grep CONFIG_STM32_USART1 .config

# 改配置后看编译列表变化
make menuconfig            # 改
make savedefconfig         # 生成精简 defconfig，diff 一下就知道动了啥
```

## 6. 导师建议：按什么顺序读

**第一天（建立地图，别碰内核）：**
1. `ld.script` → 画一张内存布局图（Flash 起止、RAM 起止、栈在哪）。
2. `board.h` → 画一张时钟树（8MHz 晶振怎么变 72MHz）+ 一张引脚表。
3. 读 `Study/02_启动流程.md` 和本文第 3 节，先有个全局印象。

**第二天（跟着启动流程走一遍，自顶向下）：**
4. `arm_vectors.c` → `stm32_start_m3m4_v1.c` → `stm32f10xxx_rcc.c` → `stm32_boot.c`
   → `nx_start.c` → `nx_bringup.c` → `stm32_bringup.c` → `nsh_main.c`。
5. **强烈建议**：用你已经配好的 VS Code + J-Link，在 `__start` 打断点，
   `runToEntryPoint: "__start"`，然后一路 `Step Over`，
   对着代码看寄存器/变量变化——比读十遍源码都管用。
   （想看最开头,在 `arm_vectors.c` 的 `start` 上打断点,单步那条 `b __start`。）

**第三天（挑一条竖线打穿：串口）：**
6. 从 `nsh> ` 的一次按键回显出发，逆流而上：
   `nsh_parse` ← `readline` ← `read(/dev/console)` ← `drivers/serial/serial.c`
   ← `stm32_serial_m3m4_v1v2v3v4.c` 的 RX 中断 ← `arm_doirq` ← `exception_common`。
   把“上半部/下半部 + ops 表”这个套路吃透。

**第四天（调度器）：**
7. 再读一遍 `nx_start.c`（这次关注 TCB、就绪链表初始化），
   然后 `sched_addreadytorun.c` / `sched_removereadytorun.c` / `sem_wait.c` / `sem_post.c`，
   最后 `arm_svcall.c` + `arm_exception.S` 看寄存器现场怎么保存/恢复。
8. 做个实验：NSH 里跑两个后台任务，在 `sched_addreadytorun` 打条件断点，观察抢占。

**顺序上的三个“不要”：**
- **不要**一上来就逐行啃链接脚本语法——先知道它“分配了什么”，语法细节用到再查。
- **不要**从启动汇编开始死抠——ARMv7-M 的“汇编”其实很少，`arm_exception.S` 一个文件，
  等你理解了上下文切换的**目的**再回来看它的实现。
- **不要**广度铺开读 `arch/arm/src/common/stm32/` 里几百个外设文件——
  只读你这块板子实际编进去的那几个（第 2.2 节的表），其余用到再看。

**长期习惯：**
- `Documentation/` 里 `Documentation/guides/` 和 `Documentation/reference/` 是官方参考，遇到概念先查这里。
- 用 Sourcetrail（`Study/12_Sourcetrail使用教程.md`）看调用图/被调关系，比全局搜索高效。
- 每看懂一条链，就在自己的笔记里画一张“函数调用 + 文件路径”的图——一个月后你会感谢自己。
