# 两个独立 example + NSH 统一管理切换

> 本文是《NuttX 源码学习文档》第 18 篇，第 16 篇《LED跑马灯实操》的进阶。
>
> **目标**：在 `apps/examples/` 下做**两个各自独立**的任务，控制同一对 LED，
> 学会用 NSH 把它们管起来、随时切换；其中任务 2 的亮灭时长能在串口里实时调。
>
> ```
> apps/examples/marquee/    ← 任务1  固定 200ms 交替
> apps/examples/mqtune/     ← 任务2  亮灭时长可调
> ```
>
> 两个目录**互不引用、互不知道对方**，谁跑谁停完全由 NSH 决定 —— 这正是
> 本文要教的东西。

---

## 1. 先搞清楚：NSH 到底是怎么"管理任务"的

很多人以为 `nsh> marquee` 是"调用一个函数"。不是。完整链路：

```
你在串口敲:  marquee &
      │
      ▼
nsh_parse()                 apps/nshlib/nsh_parse.c
      │  拆出命令名 "marquee"，发现末尾有 &  -> 标记为后台
      ▼
nsh_builtin()               apps/nshlib/nsh_builtin.c
      │  在 builtin 命令表里按名字查
      ▼
g_builtins[]                apps/builtin/builtin_list.h  (编译时自动生成)
      │  { "marquee", 100, 2048, marquee_main }
      │     名字      优先级 栈大小  入口函数
      ▼
task_spawn("marquee", marquee_main, ...)
      │
      ▼
【一个全新的、独立的 NuttX 任务】跑 marquee_main(argc, argv)
   - 有自己的 TCB、自己的 2048 字节栈、自己的 PID
   - 优先级 100，和 nsh 一样
   - 前台(不加 &): nsh 调 waitpid() 等它结束 -> shell 被占住
   - 后台(加了 &): nsh 不等，立刻打印下一个 nsh> 提示符
```

**所以"两个任务"= 两个 builtin 程序，各自被 spawn 成独立任务。**
NSH 就是那个"任务管理器"，它提供的管理手段就三样：

| 手段 | 作用 |
|---|---|
| `命令 &` | 后台启动一个任务，shell 不阻塞 |
| `ps` | 列出所有任务：PID / 优先级 / 状态 / 名字 |
| `kill -<信号> <pid>` | 给指定任务发信号（`-9` = SIGKILL 强杀） |

> 本板已经把这些开关都打开了：`CONFIG_NSH_BUILTIN_APPS=y`（认 builtin 命令）、
> `CONFIG_NSH_DISABLE_KILL` 未设（有 `kill`）、`CONFIG_SIG_DEFAULT=y` +
> `CONFIG_SIG_SIGKILL_ACTION=y`（信号真能杀掉任务）、`CONFIG_TTY_SIGINT=y`（Ctrl-C）。
> 少任何一个，`kill` 都会"看着执行了但任务不死"。

## 2. 目录结构：两个独立 example

每个 example 都是**自包含**的 4 件套，一个都不能少（见第 17 篇之前讲过的组成）：

```
apps/examples/marquee/          apps/examples/mqtune/
├── Kconfig        菜单开关      ├── Kconfig
├── Make.defs      登记目录      ├── Make.defs
├── Makefile       怎么编        ├── Makefile
└── marquee_main.c 程序本体      └── mqtune_main.c
```

| 文件 | 作用 | 关键内容 |
|---|---|---|
| `Kconfig` | menuconfig 里出现的开关 | `config EXAMPLES_MQTUNE` + 子选项 |
| `Make.defs` | 开关打开时把本目录加进待编译清单 | `CONFIGURED_APPS += $(APPDIR)/examples/mqtune` |
| `Makefile` | 程序名/优先级/栈/源文件 | `PROGNAME` `MAINSRC` + `include Application.mk` |
| `*_main.c` | `int main()` = NSH 命令的入口 | 构建系统会把它改名成 `mqtune_main` 注册 |

**两个目录之间没有任何 `#include`、没有共享 .c 文件、没有 extern 符号。**
完全独立 —— 这是本次和上一版最大的区别。

## 4. 两个关键编码技巧

### 4.1 "再敲一次命令就能控制上一次" —— flat build 共享地址空间

```c
static volatile bool g_running = false;
static volatile bool g_stopreq = false;
static volatile int  g_t0_ms   = 200;
```

```
nsh> mqtune 50 800 &     <- 后台这份在 while 里【读】 g_t0_ms
nsh> mqtune 100 100      <- 前台又 spawn 一份 mqtune，只【写】 g_t0_ms 就退出
```

两次调用的 `g_t0_ms` 是**同一块内存**。为什么？

> 本板是 NuttX **flat build**（`CONFIG_BUILD_FLAT`，默认）：内核 + 所有 app
> 编进同一个 `nuttx` ELF、跑在同一地址空间，没有 MMU 隔离。
> 同一个程序被 spawn 两次 = 两个 TCB / 两个栈，但**静态变量只有一份**。
>
> 如果是 `BUILD_PROTECTED` / `BUILD_KERNEL`，app 各有独立地址空间，
> 这招就失效了，得改用共享内存 / 消息队列 / 或把参数存到驱动里。

`volatile` 不能省：变量被两个执行流访问，不加的话编译器会把
`while (!g_stopreq)` 的判断结果缓存进寄存器 → 永不退出的死循环。

### 4.2 可打断的睡眠 —— `stop` 才跟手

```c
#define SLICE_MS 20

static bool sleep_ms(int ms)
{
  int left = ms;
  while (left > 0)
    {
      int slice;
      if (g_stopreq) return false;          /* 每 20ms 看一眼 */
      slice = (left > SLICE_MS) ? SLICE_MS : left;
      usleep(slice * 1000);                 /* usleep 单位是微秒 */
      left -= slice;
    }
  return !g_stopreq;
}
```

直接 `usleep(g_t1_ms * 1000)` 的话，设了 `mqtune 50 5000` 再敲 `stop`，
最坏要等 5 秒才停。切片后最多延迟 20ms。**这是嵌入式里通用的"可取消等待"写法。**

## 5. 实操：NSH 下切换两个任务

串口 115200 8N1，按 RESET 看到 `nsh>` 后。

### 5.1 方式 A —— 用每个 app 自带的 `stop`（推荐，最顺手）

```
nsh> marquee &                    ← 任务1 后台跑, shell 立刻回来
marquee: 启动 (固定 200 ms). 停止: marquee stop
nsh>

nsh> marquee status
marquee: 运行中 (固定 200 ms)

nsh> marquee stop                 ← 停任务1
marquee: 已请求停止
marquee: 已退出

nsh> mqtune 50 800 &              ← 切到任务2
mqtune: 启动 -> LED0 50, LED1 800, 间隔 0 (ms)

nsh> mqtune 100 100               ← 运行中改参数, 灯不闪断
mqtune: 参数已更新 -> LED0 100, LED1 100, 间隔 0 (ms)

nsh> mqtune 200 200 300           ← 加"两灯之间全灭 300ms"
nsh> mqtune stop                  ← 停任务2
```

### 5.2 方式 B —— 纯 NSH 管理（`ps` + `kill`，通用手段）

这套对**任何** app 都管用，不需要 app 自己实现 `stop`：

```
nsh> mqtune 300 300 &
nsh> ps
  PID GROUP PRI POLICY   TYPE    NPX STATE    EVENT     SIGMASK   STACK  COMMAND
    0     0   0 FIFO     Kthread   - Ready              0000...   1024   Idle_Task
    2     2 100 RR       Task      - Running            0000...   2048   nsh_main
    5     5 100 RR       Task      - Waiting  Semaphore 0000...   2048   mqtune
                                                                          ↑ 就是它

nsh> kill -9 5                    ← 强杀 PID 5
nsh> ps                           ← 确认没了
```

> ⚠ `kill -9` 是**硬杀**：任务当场消失，`main()` 里"熄灯 + close(fd)"的收尾代码
> **不会执行**，所以灯会停在最后那一帧（可能一直亮着），文件描述符也泄漏了。
> 所以优先用方式 A 的 `stop` —— 那是"请求它自己退出"，收尾干净。
>
> `kill` 是兜底手段：app 卡死、或者你调的是别人写的没有 stop 的程序时用。

### 5.3 前台 vs 后台

```
nsh> marquee            ← 忘了加 &，shell 被占住，再也敲不了字
                        ← 本板 CONFIG_TTY_SIGINT=y，按 Ctrl-C 可以救回来
nsh> marquee &          ← 正确姿势
```

### 5.4 命令速查

| 命令 | 作用 |
|---|---|
| `marquee &` / `marquee stop` / `marquee status` | 任务1 启/停/状态 |
| `mqtune &` | 任务2 用默认参数后台启动 |
| `mqtune <t0> <t1> &` | 任务2 启动并设参数 |
| `mqtune <t0> <t1>` | **运行中**改参数（下一帧生效） |
| `mqtune <t0> <t1> <gap>` | 再加两灯之间全灭 gap ms |
| `mqtune stop` / `mqtune status` | 停止 / 状态 |
| `ps` | 看所有任务和 PID |
| `kill -9 <pid>` | 强杀任意任务 |

范围：亮 10..10000 ms，间隔 0..10000 ms。

### 5.5 几组好玩的参数

| 命令 | 效果 |
|---|---|
| `mqtune 60 60 &` | 快速交替，流水灯 |
| `mqtune 50 900` | 一个一闪而过、一个长亮 |
| `mqtune 300 300 700` | 亮-灭-亮-灭，慢"呼吸" |
| `mqtune 10 10` | 最快，视觉暂留下接近同时亮 |

## 6. 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| `mqtune: command not found` | ①`apps/examples/Kconfig` 没刷新（跑 `mkkconfig.sh`）②`CONFIG_EXAMPLES_MQTUNE` 没开 ③没重烧 |
| menuconfig 里找不到 mqtune | 同上①。`apps/examples/Kconfig` 已存在时 `make` 不会自动重新生成它 |
| 敲 `marquee` 后 shell 卡死 | 忘了 `&`。Ctrl-C 救回来（会硬杀，但下次命令自愈，见 §6.5）|
| `marquee &` 只打印用法就退出 | **见 §6.6**：`CONFIG_NSH_DISABLEBG=y`，NSH 不认 `&` 也不摘掉它，`&` 成了 argv[1] |
| 改了 .config 但行为没变 | **见 §6.7**：增量编译没重编受影响的文件。`make clean && make -j` |
| `kill -9` 执行了但任务还在 | 缺 `CONFIG_SIG_DEFAULT` / `CONFIG_SIG_SIGKILL_ACTION`（本板已开） |
| `kill` 后灯一直亮着 | 硬杀不跑收尾代码。现在下次敲任意子命令会自动熄灯清理(§6.5) |
| 反复 "已经在跑了 / 已请求停止" 出不来 | **见 §6.5**：Ctrl-C 或 kill -9 留下的残留状态。已用 `worker_alive()` 自愈修复 |
| 两个任务同时跑，灯乱闪 | 它们互不知道对方，都在写 `/dev/userleds`。**先停一个再起另一个** |
| `mqtune 100 100` 提示"没在跑"却启动了 | 设计如此：没在跑时这条命令就是"用新参数启动"（前台）；要后台加 `&` |
| 改了参数灯没变 | 检查 `g_t0_ms` 有没有 `volatile`；没有的话值被缓存进寄存器了 |
| 两个 example 编出来只有一个命令 | 某个目录缺 `Make.defs`，或 `Makefile` 里 `MAINSRC`/`PROGNAME` 写错 |

## 6.5 ⚠️ 必踩的坑：状态卡死 "已经在跑了 / 已请求停止" 反复横跳

**症状**

```
nsh> marquee
marquee: 已经在跑了 (先 marquee stop)
nsh> marquee stop
marquee: 已请求停止
nsh> marquee
marquee: 已经在跑了 (先 marquee stop)     ← 永远出不来，只能复位板子
```

**原因**

`g_running` 这个全局标志，**只有循环正常跑到底部的收尾代码时才会被清成 false**：

```c
  ioctl(fd, ULEDIOC_SETALL, 0);   /* 熄灯   */
  close(fd);                      /* 关设备 */
  g_running = false;              /* 清标志 */   <- 只有正常退出才走到这
```

但如果那个任务是被**硬杀**掉的 —— 前台跑时按了 **Ctrl-C**（本板 `CONFIG_TTY_SIGINT=y`
+ `CONFIG_SIG_SIGKILL_ACTION=y`，SIGINT 的默认动作就是**当场终止任务**），
或者 `kill -9` —— 收尾代码**一行都不会执行**：

```
任务没了  →  但 g_running 还是 true
         →  marquee      看到 true, 说"已经在跑了"
         →  marquee stop 把 g_stopreq 置 true, 但【没有任何循环在消费它】
         →  死锁
```

**修法：不要只信一个 bool，去问内核那个任务还在不在**

```c
static volatile pid_t g_pid = -1;      /* 记住跑循环的那个任务 */

static bool worker_alive(void)
{
  if (!g_running) return false;

  if (g_pid > 0 && kill(g_pid, 0) == 0)   /* signo=0: 只做存在性检查, 不发信号 */
    {
      return true;                        /* 真的还在跑 */
    }

  /* 记录说在跑, 但那个 PID 已经没了 -> 上次被硬杀, 清理残留 */
  printf("marquee: 清理上次异常退出的残留状态\n");
  g_running = false;
  g_stopreq = false;
  g_pid     = -1;
  leds_off();                             /* 顺手把可能亮着的灯灭掉 */
  return false;
}
```

> `kill(pid, 0)` 是 POSIX 的标准用法："只做错误检查，不真的发信号"。
> NuttX 的实现见 `sched/signal/sig_kill.c`：
> `if (signo == 0) return (nxsched_get_tcb(pid) != NULL) ? 0 : -ESRCH;`

然后把所有 `if (g_running)` 换成 `if (worker_alive())`，状态就能自愈了。

**本工程采用的方案：只用上面这一招（状态自愈）**

只加 `worker_alive()` 就够用了，`stop` 依然是"只置标志、立刻返回"。
代价和边界要清楚：

| 场景 | 表现 |
|---|---|
| Ctrl-C 打断前台的 `marquee` | 任务被硬杀，灯停在最后一帧、fd 泄漏一次。**下次敲任意子命令**会打印"清理上次异常退出的残留状态"并自动熄灯 —— 不用复位板子 |
| `kill -9 <pid>` | 同上，自愈 |
| `stop` 后**马上**再敲 `marquee` | 循环最多要 `SLICE_MS`(20ms) 才退出。手敲肯定超过 20ms，所以基本看不到；真撞上就再敲一次 |

**另外两种可选加强**（本工程没用，知道有这回事即可）：

1. **给 Ctrl-C 装处理函数**，让它走优雅退出而不是硬杀：

   ```c
   static void on_sigint(int signo) { (void)signo; g_stopreq = true; }
   ...
   signal(SIGINT, on_sigint);        /* 进循环前装上 */
   ```

   装了之后 SIGINT 不再执行"终止任务"的默认动作，收尾代码能跑到。
   代价：Ctrl-C 不再能强行中断（万一循环卡死就真出不来了）。

2. **让 `stop` 等它真退出再返回**：

   ```c
   g_stopreq = true;
   for (i = 0; i < 100 && g_running; i++) usleep(10 * 1000);   /* 最多 1s */
   ```

   好处是 `stop` 返回时状态一定干净；代价是 `stop` 命令本身要阻塞一下。

**教训**：只要状态是"跨任务共享的全局变量"，就必须考虑
**持有者被异常杀死后谁来清理**。这在 RTOS 里是通用问题，
不管你用全局变量、信号量还是文件锁都一样。

## 6.6 ⚠️ `marquee &` 打印用法就退出 —— 后台支持的两道闸

**症状**

```
nsh> marquee &
用法:
  marquee &         后台启动固定节奏跑马灯 (200 ms)
  ...
nsh> marquee status
marquee: 已停止
```

`marquee`（不加 `&`）能跑，加了 `&` 就只打印用法。

**直接原因：NSH 不认识 `&`，也不把它摘掉**

`apps/nshlib/nsh_parse.c`：

```c
  /* Check if the command should run in background */

#ifndef CONFIG_NSH_DISABLEBG
  if (argc > 1 && strcmp(argv[argc - 1], "&") == 0)
    {
      vtbl->np.np_bg = true;
      argc--;                 /* ★ 把 "&" 从参数里摘掉 */
    }
#endif
```

这段被编译掉的话：不设后台标志，**也不摘掉 `&`** → 程序收到
`argc=2, argv[1]="&"` → 落进 `usage()` 分支 → **根本没进主循环**。

**关键：`CONFIG_NSH_DISABLEBG` 有两道闸，只关一道没用**

这是本次排查最坑的地方 —— 我把 Kconfig 里的开关关掉、全量重编、
回读 Flash 都对上了，`&` 还是不работ。真正的原因在
`apps/nshlib/nsh.h` 开头：

```c
/* The background commands require pthread support */

#ifdef CONFIG_DISABLE_PTHREAD
#  ifndef CONFIG_NSH_DISABLEBG
#    define CONFIG_NSH_DISABLEBG 1      /* ★ 强制把它定义回来 */
#  endif
#endif
```

**NSH 的后台执行依赖 pthread。** 本板是最小系统，`CONFIG_DISABLE_PTHREAD=y`，
于是不管你在 Kconfig 里怎么设，`nsh.h` 都会把 `CONFIG_NSH_DISABLEBG` 定义回来。

```
Kconfig: # CONFIG_NSH_DISABLEBG is not set     ← 你以为开了
nsh.h:   #define CONFIG_NSH_DISABLEBG 1        ← 实际被强制关掉
```

> **教训**：`.config` 不是最终真相。头文件里的"一致性检查/强制回填"
> （NuttX 里到处都是这种 `#ifdef A → #define B`）会覆盖你的配置。
> 光看 `.config` 和 `include/nuttx/config.h` 都不够 —— 得看**预处理结果**。

**正确修法：两个开关一起**

```bash
cd /home/nuttx/nuttxspace/nuttx
kconfig-tweak --disable CONFIG_DISABLE_PTHREAD    # ★ 真正的那道闸
kconfig-tweak --disable CONFIG_NSH_DISABLEBG
make olddefconfig
make clean && make -j$(nproc)                     # 改配置必须 clean，见 6.7
bash ~/bin/nuttx-flash.sh --no-build
```

代价：`.text` 约 +5.6KB（pthread 支持）。512KB Flash 无压力。

**怎么可靠验证（`grep config.h` 不够！）**

用**预处理**看那段代码到底活没活下来 —— 这是唯一能穿透"头文件强制回填"的办法：

```bash
cd /home/nuttx/nuttxspace/apps/nshlib
arm-none-eabi-gcc -E -march=armv7-m -mthumb -mfloat-abi=soft \
  -isystem /home/nuttx/nuttxspace/nuttx/include \
  -I /home/nuttx/nuttxspace/apps/include \
  -D__NuttX__ -DNDEBUG nsh_parse.c | grep -n '"&"'
```

期望看到：

```
6844:  if (argc > 1 && strcmp(argv[argc - 1], "&") == 0)
```

没有输出 = 后台支持没编进去，别浪费时间烧录了。

> 另外提醒：**别拿 `nice` 命令当后台支持的旁证** —— `nice` 有自己的开关
> `CONFIG_NSH_DISABLE_NICE`，和 `&` 不是一回事（我一开始就是这么判断错的）。

**不想开 pthread 的替代方案**

如果非要保持 `CONFIG_DISABLE_PTHREAD=y`（省那 5.6KB），就别指望 `&`，
改成**让程序自己变成后台任务**：命令本身只做 `task_create()` 起一个 worker
然后立刻返回，`nsh>` 自然就回来了，不需要 `&`。
代价是两个 example 要共用一份 worker 代码，不再"各自独立"。

## 6.7 ⚠️ 改了 `.config` 却"没生效" —— 增量编译的坑

排查 6.6 时踩到的：改完 `CONFIG_NSH_DISABLEBG` 跑 `make -j`，
**`nuttx` 的 .text 大小一个字节都没变**。

原因：NuttX/apps 的增量编译**不保证**在 `.config` 改动后重新编译所有受影响的
`.c`。`Make.dep` 里未必把 `include/nuttx/config.h` 列成每个文件的依赖，
于是那些 `#ifdef CONFIG_XXX` 的分支还是按旧配置编的旧 `.o`。

实测对比（同一个 `CONFIG_NSH_DISABLEBG` 开/关）：

| | `nsh_parse.o` | `nuttx` .text |
|---|---|---|
| 增量 `make` | 22356（两次**完全一样**） | 104066（两次一样）|
| `make clean` 后全量 | —— | **103522**（变了）|

**规矩**：

```bash
# 只改了源码 .c/.h        -> make -j 就够
# 改了 .config / Kconfig  -> make clean && make -j   ★
# 换了板子/配置           -> make distclean && ./tools/configure.sh <board>:<cfg>
```

判断"到底编进去没有"的两个笨办法（很好用）：

```bash
# 1) 看 config.h 里那个宏在不在
grep -n 'NSH_DISABLEBG' include/nuttx/config.h

# 2) 直接在 bin 里找特征字符串（strings 默认不认中文，要用 grep -a）
grep -ac '清理上次异常退出' nuttx.bin
```

## 6.8 ⚠️ `ps: command not found` —— `ps` 需要 procfs

**症状**

```
nsh> ps
nsh: ps: command not found
```

**原因**：NSH 的 `ps` 是靠读 `/proc` 实现的，两个开关都要满足：

```kconfig
config NSH_DISABLE_PS
	default DEFAULT_SMALL || !FS_PROCFS || FS_PROCFS_EXCLUDE_PROCESS
```

本板 `CONFIG_DEFAULT_SMALL=y` 且 `FS_PROCFS` 默认关 → `ps` 被裁掉了。

更坑的是：**只开 `CONFIG_FS_PROCFS=y` 还不够**。`olddefconfig` 会把
`FS_PROCFS_EXCLUDE_*` 一堆子开关按 `DEFAULT_SMALL` 全设成 `y`，
其中 `FS_PROCFS_EXCLUDE_PROCESS=y` 正好把 `ps` 要的进程条目排除掉了。

**修法**（三个开关一起）

```bash
cd /home/nuttx/nuttxspace/nuttx
kconfig-tweak --enable  CONFIG_FS_PROCFS
kconfig-tweak --disable CONFIG_FS_PROCFS_EXCLUDE_PROCESS
kconfig-tweak --disable CONFIG_NSH_DISABLE_PS
make olddefconfig
make clean && make -j$(nproc)          # 改配置必须 clean，见 6.7
bash ~/bin/nuttx-flash.sh --no-build
```

代价：`.text` 大约 +12KB（procfs 本体 ~3.5KB + 进程条目 ~8KB）。
本板 512KB Flash，完全不心疼。

`/proc` 的挂载已经由板级代码做好了，见
`boards/arm/stm32f1/m144z-m3/src/stm32_bringup.c`：

```c
#ifdef CONFIG_FS_PROCFS
  nx_mount(NULL, M144Z_M3_PROCFS_MOUNTPOINT, "procfs", 0, NULL);
#endif
```

## 6.9 怎么确认"板子上跑的到底是哪一版固件"

排查上面这些坑时，最浪费时间的就是**分不清"我改了配置"和"板子上真的是这一版"**。
三个由弱到强的手段：

**① 看 config.h（判断源码层面编不编）**

```bash
grep -c 'NSH_DISABLEBG' include/nuttx/config.h     # 0 = 后台已启用
```

**② 在 bin 里找特征字符串（判断构建产物对不对）**

```bash
# ⚠ strings 默认只认 ASCII，中文串抓不到，必须用 grep -a
grep -ac '<-heap> <pid1 pid2 ...>' nuttx.bin       # ps 的 usage，1 = ps 编进去了
grep -ac '清理上次异常退出'        nuttx.bin       # 自己代码的中文提示
```

> 挑特征串要挑**唯一且够长**的。像 `nice`、`ps` 这种两三个字母的，
> 在二进制里到处都能撞上，不能作为判据。

**③ 回读 Flash 和本地 bin 逐字节比对（最硬的证据）**

```bash
cd /home/nuttx/nuttxspace/nuttx
printf 'connect\nsavebin /tmp/rb.bin 0x08000000 0x10000\nqc\n' > /tmp/rb.jlink
JLinkExe -device STM32F103ZE -if SWD -speed 4000 -autoconnect 1 \
         -CommanderScript /tmp/rb.jlink >/dev/null
head -c 65536 nuttx.bin > /tmp/ref.bin
cmp /tmp/rb.bin /tmp/ref.bin && echo "板上就是这一版"
```

**④ 板子上自己看**

```
nsh> help          # 命令列表变了 = 固件确实换了
```

## 8. 自动切换：`marquee → mqtune → marquee → …`

手动敲命令切换太累。要让它自己循环，**该建什么文件？** 两条路：

| 方案 | 需要的文件 | 本板可行性 |
|---|---|---|
| **A. 写第三个 example 当"监工"** | `apps/examples/ledsw/` 四件套 | ✅ **推荐**，不用改任何现有配置 |
| B. NSH 脚本 + `while` 循环 | ROMFS 里的脚本文件 | ❌ 本板缺三样东西，见 8.4 |

### 8.1 方案 A 的思路：supervisor（监工进程）

新 example **`ledsw`** 自己**一个 LED 都不碰**，它做的事和你手动敲命令完全一样：

```
        你手动敲                        ledsw 内部
   nsh> marquee            <-->   exec_builtin("marquee", {"marquee", NULL})
   nsh> marquee stop       <-->   exec_builtin("marquee", {"marquee","stop",NULL})
   nsh> mqtune 80 600      <-->   exec_builtin("mqtune",  {"mqtune","80","600",NULL})
```

`exec_builtin()` 正是 **NSH 自己**用来启动内建命令的那个函数
（`apps/builtin/exec_builtin.c`，NSH 的 `nsh_builtin.c` 也是调它）。

所以 **marquee / mqtune 一行代码都不用改**，它们根本不知道有人在遥控自己。
这就是 Unix 里的 supervisor 模式：**干活的进程保持简单，另起一个进程编排它们的生命周期。**

```
              ┌──────────────┐
   nsh> ledsw │   ledsw      │  监工，不碰硬件
              │  while(!stop)│
              └──┬────────┬──┘
   exec_builtin()│        │exec_builtin()
                 ▼        ▼
           ┌─────────┐  ┌─────────┐
           │ marquee │  │ mqtune  │   各自独立，互不知情
           └────┬────┘  └────┬────┘
                └─────┬──────┘
                      ▼
                /dev/userleds
```

### 8.2 核心代码

**像 NSH 一样执行一条内建命令**：

```c
#include <builtin/builtin.h>

static int run_cmd(const char *name, const char *a1, const char *a2)
{
  FAR char *argv[4];
  int argc = 0;

  argv[argc++] = (FAR char *)name;     /* ★ argv[0] 必须是命令名本身 */
  if (a1) argv[argc++] = (FAR char *)a1;
  if (a2) argv[argc++] = (FAR char *)a2;
  argv[argc] = NULL;                   /* ★ 必须 NULL 结尾 */

  return exec_builtin(name, argv, NULL) < 0 ? -1 : 0;
}
```

**一个阶段 = 启动 → 等 N 秒 → 停止**：

```c
static bool run_phase(const char *name, const char *a1, const char *a2)
{
  run_cmd(name, a1, a2);
  g_current = name;

  if (!wait_ms(g_period * 1000))     /* 可打断的等待 */
    {
      stop_current();
      return false;                  /* 中途收到 ledsw stop */
    }

  stop_current();
  return true;
}
```

**主循环**：

```c
  while (!g_stopreq)
    {
      if (!run_phase("marquee", NULL, NULL))  break;   /* 固定节奏  */
      if (!run_phase("mqtune", "80", "600"))  break;   /* 不对称节奏 */
    }
```

### 8.3 三个容易踩的细节

**① `stop` 是异步的，切换之间要留缓冲**

`marquee stop` 只是把 `g_stopreq` 置 true 就返回了，对方的循环最多要
`SLICE_MS`(20ms) 才真正退出、熄灯。如果紧接着就启动 mqtune，
对方还没释放，会看到"已经在跑了"。所以：

```c
#define SETTLE_MS 150

static void stop_current(void)
{
  if (g_current)
    {
      run_cmd(g_current, "stop", NULL);
      usleep(SETTLE_MS * 1000);      /* ★ 等它真退出 */
      g_current = NULL;
    }
}
```

**② 等待必须可打断**

`sleep(5)` 的话，敲 `ledsw stop` 最坏要等 5 秒。同样切片：

```c
static bool wait_ms(int ms)
{
  int left = ms;
  while (left > 0)
    {
      int slice;
      if (g_stopreq) return false;
      slice = (left > SLICE_MS) ? SLICE_MS : left;   /* SLICE_MS = 100 */
      usleep(slice * 1000);
      left -= slice;
    }
  return !g_stopreq;
}
```

**③ 启动前 / 退出时都要清场**

```c
  /* 启动前：把可能残留在跑的都停掉，保证从干净状态开始 */
  run_cmd("marquee", "stop", NULL);
  run_cmd("mqtune",  "stop", NULL);
  usleep(SETTLE_MS * 1000);

  ... while 循环 ...

  /* 退出时：确保两个 demo 都停了，别留个灯亮着 */
  stop_current();
  run_cmd("marquee", "stop", NULL);
  run_cmd("mqtune",  "stop", NULL);
```

另外 `ledsw` 自己也用了和 marquee/mqtune 一样的 `worker_alive()` 自愈
（见 §6.5），被 Ctrl-C 硬杀后不会卡死。

### 8.4 方案 B：NSH 脚本 —— 本板暂时走不通

理想中是这样：

```sh
# /etc/init.d/ledloop
while true
do
  marquee &
  sleep 5
  marquee stop
  mqtune 80 600 &
  sleep 5
  mqtune stop
done
```

但本板当前配置缺三样：

```
CONFIG_NSH_DISABLE_LOOPS=y      ← 没有 while/until
CONFIG_NSH_DISABLE_SOURCE=y     ← 没有 source/. 命令
# CONFIG_FS_ROMFS is not set    ← 没有文件系统，脚本没地方放
```

要走这条路得补齐：

```bash
kconfig-tweak --disable CONFIG_NSH_DISABLE_LOOPS
kconfig-tweak --disable CONFIG_NSH_DISABLE_SOURCE
kconfig-tweak --enable  CONFIG_FS_ROMFS
kconfig-tweak --enable  CONFIG_NSH_ROMFSETC      # 把 /etc 做成 romfs 编进固件
make olddefconfig && make clean && make -j$(nproc)
```

还要用 `tools/mkromfsimg.sh` 把脚本打包成 romfs 镜像。
**代价明显更大**，而且脚本能力有限（NSH 不是 bash）。
所以本工程选方案 A。

### 8.5 建的文件清单

和前两个 example 一样的四件套，一个都不少：

```
apps/examples/ledsw/
├── Kconfig          # config EXAMPLES_LEDSW，depends on EXAMPLES_MARQUEE && EXAMPLES_MQTUNE && BUILTIN
├── Make.defs        # CONFIGURED_APPS += $(APPDIR)/examples/ledsw
├── Makefile         # PROGNAME/PRIORITY/STACKSIZE + MAINSRC = ledsw_main.c
└── ledsw_main.c     # supervisor 主体
```

`Kconfig` 里的 `depends on` 很关键 —— 少了任何一个被监工的 example，
`ledsw` 就没意义，让 menuconfig 直接把它灰掉。

```bash
cd /home/nuttx/nuttxspace/apps/examples
bash ../tools/mkkconfig.sh -m "Examples"        # 新建 example 必做(见 §3.5)
cd ../../nuttx
kconfig-tweak --enable CONFIG_EXAMPLES_LEDSW
make olddefconfig && make clean && make -j$(nproc)
bash ~/bin/nuttx-flash.sh --no-build
```

### 8.6 用法

```
nsh> ledsw &            后台自动循环, 每段 5 秒
ledsw: 启动自动切换, 每段 5 秒. 停止: ledsw stop
ledsw: --> marquee
ledsw: --> mqtune
ledsw: --> marquee
...

nsh> ledsw 3 &          每段 3 秒
nsh> ledsw status
nsh> ledsw stop         停止, 并把当前 demo 一起停掉
nsh> ps                 确认三个任务都没了
```

| 命令 | 作用 |
|---|---|
| `ledsw &` | 后台自动循环（每段秒数取 Kconfig 默认） |
| `ledsw <秒> &` | 指定每段多少秒（1..600） |
| `ledsw stop` | 停止调度并停掉当前 demo |
| `ledsw status` | 状态 + 当前跑的是哪个 |

> 手动模式完全不受影响：`ledsw stop` 之后照样可以单独 `marquee &` / `mqtune 50 800 &`。
