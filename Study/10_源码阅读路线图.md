## 2. 阅读源码的工具方法

### 2.1 定位代码

```bash
# 找函数定义
grep -rn "^.*函数名(" --include="*.c" --include="*.h" sched/ fs/ include/

# 找宏定义
grep -rn "CONFIG_XXX" include/ Kconfig

# 找所有调用点（理解函数用途）
grep -rn "函数名" --include="*.c" --include="*.h" . | grep -v "\.o\|\.gc"

# 找注册点（驱动/文件系统）
grep -rn "register_driver\|register_mountpoint" --include="*.c" drivers/ fs/
```

### 2.2 阅读策略

1. **先数据结构，后代码逻辑**：找 `struct xxx_s` 定义，字段注释就是设计文档
2. **从入口函数往回读**：如读调度就找 `nxsched_add_readytorun` 被谁调用
3. **忽略配置无关代码**：`#ifdef CONFIG_XXX` 块，先看默认配置路径
4. **交叉引用头文件**：`include/nuttx/xxx.h` 是子系统对外的"接口契约"
5. **利用官方文档**：Documentation/ 目录（.rst），特别是：
   - `Documentation/introduction/` 架构介绍
   - `Documentation/components/` 各子系统详解
   - 板子页面 `Documentation/platforms/`

### 2.3 高效工具组合

```bash
# ctags 生成索引（推荐）
ctags -R --languages=C .

# 在 vim 里 Ctrl-] 跳转定义，Ctrl-t 返回
# 或使用 vscode + clangd（配置 compile_commands.json 后体验最佳）

# 查看符号在哪个文件
grep -rn "符号名" --include="*.h" include/nuttx/ | head

# 查看系统调用面
head -50 syscall/syscall.csv
```

## 3. 调试技巧

### 3.1 日志

- 打开 `CONFIG_DEBUG_INFO` + `CONFIG_DEBUG_SCHED` 等，`info()` 宏输出调试信息
- 驱动/内核用 `_info()`（syslog），用户态用 `printf`
- 关键区监控：`CONFIG_SCHED_CRITMONITOR`（打印调度延迟峰值）

### 3.2 断言与检查

- `DEBUGASSERT()`：遍布内核，触发时打印文件名行号
- `CONFIG_DEBUG_ASSERTIONS` + `CONFIG_DEBUG_MM`：内存越界检查
- KASAN（mm/kasan/）：use-after-free 检测

### 3.3 运行时信息

```bash
# NSH 里查看运行状态
ps          # 任务列表（含状态/优先级/栈用量）
free        # 内存统计
cat /proc/meminfo
cat /proc/interrupts   # 中断统计
cat /proc/version
```

### 3.4 调试器

- OpenOCD + GDB：`arm-none-eabi-gdb nuttx`，`target remote :3333`
- 常用断点：`nx_start`、`nxsched_add_readytorun`、`sem_post`、驱动 ISR
- 注意：NuttX 大量优化（`-O2`），调试建议加 `CONFIG_DEBUG_OPTLEVEL="-O0"`（或 Kconfig 里的优化选项）

## 6. 使用 Sourcetrail 可视化阅读

项目已配置好 Sourcetrail 索引（见 Study/tools/ 说明），启动方式：

```bash
sourcetrail                          # 启动 GUI
# 或直接打开项目：
sourcetrail /home/nuttx/nuttxspace/nuttx.srctrlprj
```

- 索引数据库：/home/nuttx/nuttxspace/nuttx.srctrldb（首次索引约 1201 个文件）
- 索引数据源：/home/nuttx/nuttxspace/nuttx/compile_commands.json（由构建日志解析生成）
- 代码变更后重新索引：Sourcetrail GUI 里点 "Index"（增量），或命令行：

```bash
sourcetrail index --full --project-file=/home/nuttx/nuttxspace/nuttx.srctrlprj
```

重新生成 compile_commands.json（代码变更或换配置后）：

```bash
cd /home/nuttx/nuttxspace/nuttx
make clean && make -j28 V=1 > /tmp/build.log 2>&1
python3 Study/tools/parse_compile_commands.py /tmp/build.log \
    "/home/nuttx/nuttxspace/nuttx,/home/nuttx/nuttxspace/apps" \
    /home/nuttx/nuttxspace/nuttx/compile_commands.json
```

Sourcetrail 使用要点：
- 点一个符号（函数/类型/宏），左侧显示所有调用者，右侧显示被调用者
- 用 `Ctrl+Shift+F` 全局搜索符号
- 配合本文档按图索骥：先在文档里找到关键函数名，再到 Sourcetrail 里看它的调用图

## 7. 常见"劝退点"与应对

| 劝退点 | 应对 |
|--------|------|
| CONFIG_XXX 太多，代码跳来跳去 | 只看默认配置路径；用 Kconfig 查宏含义 |
| 汇编启动代码看不懂 | 先跳过，从 nx_start() 开始；回头再看 |
| 架构目录巨大（166MB） | 只看你板子对应芯片目录，其余无视 |
| 中断/上下文切换太绕 | 先理解"任务栈上预置虚假上下文"这一思想，再看具体实现 |
| 函数名前缀多（nx_/nxsem_/psock_） | 见 08_系统调用.md 第 5 节的命名约定表 |

## 8. 本 Study 目录的使用建议

- 每篇文档都标注了"建议阅读顺序"与具体文件路径，按图索骥
- 阅读时在文档上做笔记：在对应章节补充你看到的代码行号
- 发现文档与代码不符时，直接修改文档（它是你的学习资产）
- 全部读完后，试着不看文档画出：启动流程图、调度框图、open() 调用链
